# atem-sweep

The tool the emulator was rebuilt with, and the check that keeps it honest.
Blackmagic publishes the ATEM switcher SDK (BMDSwitcherAPI, 10.2.1 here), not
the network protocol under it. atem-sweep drives a switcher through the SDK —
every safe function the ATEM Mini has, good input and bad — and records
exactly how it answers: against the **real ATEM** that makes a golden record;
against the **emulator** it checks every answer against that record.

Which functions it covers, how they are grouped, what a verification
compares and the recorded results: [sdk-functions.md](sdk-functions.md).

## A test client plus a recording proxy

atem-sweep is two things in one program:

- **The test client** runs the tests through the Blackmagic SDK. It never
  speaks the protocol itself: the SDK does, and the sweep records what the
  SDK reports (return codes, read-backs, callbacks) in `results.json`.
- **The recording proxy** ([wireproxy.cpp](../sweep/src/wireproxy.cpp)) sits
  in the middle. It listens on `127.0.0.1:9910` like a switcher, relays every
  packet to the real one (a connection of its own per client) and back, and
  records both directions, split into fields, in `wire.jsonl`. That is how
  the golden record has the switcher's exact bytes, not only what the SDK
  made of them.

```text
record:    atem-sweep tests ─► SDK ─► proxy 127.0.0.1 ─► real ATEM
                                      (records both ways)

verify:    atem-sweep tests ─► SDK ─► proxy 127.0.0.1 ─► emulator 127.0.0.2
                                      (records both ways)

--capture: any client, e.g. ─────────► proxy 127.0.0.1 ─► real ATEM or emulator
           ATEM Software Control      (records both ways, no tests)
```

The proxy only relays: something real has to answer behind it. The emulator
listens on its own loopback address (`atem-emu --listen 127.0.0.2`) so the
proxy can keep 127.0.0.1. Over USB there is nothing to relay: no wire
capture, and no verified backup.

## From a recording to the emulator

```text
 1 record    atem-sweep 192.168.0.240 --protect    ─► golden record
                                                      results.json, wire.jsonl
 2 profile   core/make_profile.py                  ─► core/profiles/<name>
                                                      the startup state, macros
 3 behaviour core/tools/setters_spec.py (checked by check_setters.py,
             generated by gen_setters.py) + core/src/device.cpp
 4 verify    atem-emu --listen 127.0.0.2 --profile <name>
             atem-sweep 127.0.0.2 --verify golden\<record>\results.json
 5 differences: each failing test lists what the real ATEM answered and
             what the emulator did; its commands and answers are in both
             runs' wire.jsonl ─► back to 3
```

1. **Record** the real ATEM through the proxy (see [Safety](#safety) and
   [Backup](#backup)); the run becomes a golden record under `sweep/golden/`
   with [slim_record.py](../sweep/slim_record.py).
2. **Profile.** [make_profile.py](../core/make_profile.py) takes the connect
   dump (every field the switcher sends a new client) and what each stored
   macro changed; `--backup` adds the stored macros' bytes from a backup.
3. **Behaviour.** Most "set value" commands are a table in
   [setters_spec.py](../core/tools/setters_spec.py), proven against the
   recording before any C++ is built; actions, transfers and quirks are
   handlers in `core/src/device.cpp` ([core.md](core.md)).
4. **Verify** the emulator against the golden record.
5. **Close the differences.** A diff says *what* differs (a read-back, a
   callback that did or didn't fire); the per-test `wire` (the commands sent
   and the fields that came back) and `wire.jsonl` of both runs say *why*.
   The core was built this way with an AI coding agent reading the
   recordings, writing the rule and re-running the verify
   ([overview.md](overview.md#where-ai-comes-in)). The golden record is never
   edited to make a test pass.

**When the emulator should learn something new:** add a sweep test (or let
[gen_tests.py](../sweep/coverage/gen_tests.py) generate it), record the real
ATEM, then steps 2–5. **After a firmware or SDK update:** record a new golden
record in its own folder and keep the old one — the differences between the
two are the change — then steps 2–5.

## Safety

It **reads everything**, **changes settings and puts each back** (checked
per test: program / preview, keys, PiP, transitions, colour generators, the
HDMI-out source, Fairlight audio, …) and **runs / stops the stored macros**.

**Stored content** — macros and stills — is created, listed, changed and
deleted only by the storage tests, and only inside a **backup-protected
run**: a complete backup first (the storage tests are skipped otherwise),
then the tests, which use empty slots and delete what they make, then the
backup is restored and verified (see [Backup](#backup)). That needs Ethernet
(the recording proxy).

It **never** saves or clears the startup state (it can't be read back),
changes the video mode (every output goes black), records or streams
([the excluded functions](sdk-functions.md#excluded-functions)).

What "puts them back" covers is exactly the settings in the snapshot
([snapshot.cpp](../sweep/src/snapshot.cpp)), taken right after connecting.
At the end each one is set back and checked, then everything is read back
and compared; any setting that could not be read at the start, could not be
set, or differs afterwards is listed and the run fails (exit code 5). **Your
stored macros can change settings outside the snapshot** (audio, for
example) when the macro tests run them; those are not restored.

It will not start (exit code 4, nothing changed) while a macro is being
recorded or is running: the sweep's commands would end up in the recording.

It does visibly and audibly change the live output while it runs (inputs
switch, the PiP moves, macros run, a short fade to black, the HDMI output's
source and audio levels change for a moment), so run it when the switcher is
not in use; it asks before starting (`--yes` skips the question).

Opt-in: `--allow-camera` sends camera actions that move a lens (autofocus);
`--allow-mic-power` lets a test switch the mic inputs' plug-in power *on*
(setting what it already is, switching it off and back on, and invalid
values run without it).

## Running it

```powershell
# Record the real ATEM (over Ethernet): golden record + wire capture.
# --protect: back up stored content first, restore and check it after.
atem-sweep 192.168.0.240 --protect

# Verify the emulator (on this PC) against a golden record
atem-emu --listen 127.0.0.2 --profile ..\core\profiles\atem-mini_proto2.30_2026-09-28
atem-sweep 127.0.0.2 --verify golden\atem-mini_sdk10.2.1_proto2.30_2026-09-28\results.json

atem-sweep usb                                  # over USB: SDK behaviour only, no wire capture
atem-sweep --list                               # all tests
atem-sweep 192.168.0.240 --only fly.            # tests whose id starts with fly.
atem-sweep 192.168.0.240 --groups storage       # one or more test groups

# Make a golden record from a run (cuts transferred picture bytes)
python slim_record.py runs\<run> golden\<name>
```

Before a run against the emulator, the emulator must already own
`127.0.0.2:9910`: when nothing answers at an address, the SDK falls back to
an ATEM on this PC's USB. (Two connect tests use exactly that on purpose; see
[sdk-functions.md](sdk-functions.md#the-usb-fallback).)

| Option | Meaning |
|---|---|
| `--verify FILE` | compare with a golden record instead of recording |
| `--only PREFIX`, `--groups LIST` | run part of the sweep (`connect.main` always runs); the groups are in [sdk-functions.md](sdk-functions.md#test-groups) |
| `--protect` | on a real switcher: backup before, restore and verify after, even without the storage tests |
| `--yes` | don't ask before changing the switcher's output |
| `--out DIR` | output folder (default `runs\<time>-<mode>`) |
| `--no-proxy` | no wire capture (the SDK talks to the target directly) |
| `--allow-camera`, `--allow-mic-power` | opt-in actions (see [Safety](#safety)) |
| `--json` | also print the plan, each result and the run's phases as `@@` + one JSON object per line (for atem-sweep-gui) |
| `--stop-file PATH` | stop after the current test once the file exists; everything is put back as usual |
| `--backup`, `--restore DIR`, `--compare A B` | [Backup](#backup) |
| `--capture SECONDS` | [capture another client](#capturing-another-client) |

| Exit code | Meaning |
|---|---|
| 0 | all passed |
| 1 | a test failed or differs from the golden record |
| 2 | could not start: bad golden record, output folder, proxy |
| 3 | results could not be written, or a backup is incomplete |
| 4 | a macro was recording / running: nothing was changed |
| 5 | the switcher was not completely put back (settings or stored content) |
| 6 | declined at the "Continue?" question: nothing was done |

Each run writes `runs\<time>-<mode>\`: `results.json` (per test: status,
every observation, the SDK callbacks fired, the SDK functions called and —
through the proxy — the fields sent and received; verify runs add `diffs`),
`wire.jsonl` (every UDP packet, both directions, split into fields) and
`coverage.txt`. Details: [sdk-functions.md](sdk-functions.md#output).

Needs ATEM Software Control installed (the SDK's COM library) and Qt's `bin`
folder on `PATH` (or `windeployqt atem-sweep.exe`).

## atem-sweep-gui

`atem-sweep-gui.exe` (next to `atem-sweep.exe`) runs the sweep and shows it
as a coverage map: every test is a square, grouped by
[test group](sdk-functions.md#test-groups), coloured as it runs (same as the
real ATEM, differs, skipped).

- **Emulator** verifies the emulator against a golden record. The GUI starts
  `atem-emu --listen 127.0.0.2` with the matching profile, and only starts
  the sweep once that process owns 127.0.0.2:9910. It stops the emulator
  afterwards.
- **Real ATEM** records a new run: it asks first, then backs up, sweeps, puts
  the settings back, backs up what the sweep left, restores the stored
  content and checks it; the steps show above the map. **Stop** finishes the
  current test and puts everything back.
- A checkbox per group takes it out of the run. The list on the right drills
  in — interface, property, each value — with both values where the
  emulator differs; pointing at a row lights up its squares.
- **Backup ATEM** (real ATEM only) shows the backups grouped by sweep, with
  **Backup now**, and **Folder** and **Restore** per backup (restore asks
  first and checks after).
- **Download report** saves every test with its group, values and SDK
  functions as a Markdown file.

For documentation: `--screenshot FILE` (with `--iface NAME [--prop NAME]` or
`--backups`) saves a view and exits; `--selftest GROUPS --screenshot FILE`
runs those groups against the emulator first.

## Capturing another client

To see what another client — ATEM Software Control, say — sends and gets,
run only the proxy and point the client at `127.0.0.1` (by IP: USB can't be
captured):

```powershell
atem-sweep 192.168.0.240 --capture 600 --out runs\asc      # the real ATEM
atem-sweep 127.0.0.2 --capture 600 --out runs\asc-emu      # the emulator
```

It stops after the given seconds, or when a file named `stop` appears in the
output folder, and writes `wire.jsonl`. Comparing the two captures shows what
the client needs that the emulator doesn't do yet. Anything you change in the
client during a capture really happens on the switcher. (Not yet done with
ATEM Software Control.)

## Backup

A full backup of the switcher through the SDK, so that tests which create,
change and delete stored content can run safely and everything can be put
back. Backups are a safety net and a troubleshooting aid only; the
reverse-engineering data is the tests' recordings.

```powershell
atem-sweep 192.168.0.240 --backup            # read-only; into backups\<time>
atem-sweep --compare backups\A backups\B     # 0 = identical, 1 = differences
atem-sweep 192.168.0.240 --restore backups\A # put macros + stills back, then verify
```

```text
┌──────────┐    ┌──────────────────────┐    ┌──────────┐    ┌──────────┐    ┌──────────────┐
│ -before  │───►│ tests: create, list, │───►│ -swept   │───►│ restore  │───►│ -after       │
│          │    │ change, delete, ...  │    │          │    │ from     │    │ compared     │
│          │    │                      │    │          │    │ -before  │    │ with -before │
└──────────┘    └──────────┬───────────┘    └──────────┘    └──────────┘    └──────────────┘
 state, macros,            ▼                 what the tests  macros and      must be
 stills          results.json, wire.jsonl    left behind     stills          identical
```

A protected run takes those three backups; the verdict is in
`-after\restore-check.json`.

| In the backup folder | What |
|---|---|
| `manifest.json` | target, product, time, every macro and still slot in use (name, description, size, SHA-256; stills also the switcher's own hash, size and pixel format), and any problem |
| `state.txt` | the connect dump: every state field the switcher sends a new client (364 on the ATEM Mini), one `NAME HEX` per line. Needs Ethernet: over USB there is no state |
| `macros/NN.bin` | each stored macro's bytes (`MacroPool::Download`) |
| `stills/NN.raw` | each stored still's frame as the switcher sends it (the ATEM Mini: 10-bit YUVA, 1920×1080) |
| `restore-check.json` | after a restore (or a protected run's `-after`): which backup it was compared with, and whether identical |

Taking a backup only downloads; it never changes the switcher. A backup that
misses anything says so (`"complete": false`, exit code 3). Backups go to
`sweep/backups/`, which git ignores: they hold your stored macros and stills.

**Restore** checks every backup file's checksum and that it is the same
product, refuses while a macro runs or records, and asks first (`--yes`
skips). Macros are uploaded when their bytes differ, renamed when only the
name or description does, deleted when the backup's slot is empty; stills
the same, by the switcher's hash. Settings are not written by the restore
(the sweep puts back the settings its tests change). Then it waits 10 s,
takes a new backup and compares it with the one restored: exit 0 only when
identical, 5 when anything differs.

Verified on the real ATEM Mini (2026-09-28): backup A, restore a test backup
(a macro and a still added, a macro and a still renamed), restore A,
verification backup identical to A — all 364 state fields, the 4 macros'
bytes and the 3 stills' hashes. Found on the way:

- Macro names are cut to 20 characters.
- For a few seconds after stored content changes, a new client's connect
  dump still shows some old content (e.g. a deleted macro as used), which the
  switcher corrects with updates right after the dump; hence the 10 s wait.
- Unused bytes of many state fields hold leftovers (pieces of names); they
  change with the stored content and come back when it does.

## Layout and build

```text
sweep/
├── CMakeLists.txt        atem-sweep and atem-sweep-gui
├── slim_record.py        run → golden record (cuts transfer payloads)
├── golden/               the golden records
├── backups/              backups (git-ignored: your macros and stills)
├── coverage/             gen_tests.py, categories.py, scan_usage.py and their lists
├── src/
│   ├── main.cpp           options, safety prompt, proxy, backup/restore flow
│   ├── runner.*           run loop, console, --json, golden comparison, coverage report
│   ├── groups.h           the five test groups (shared with the GUI)
│   ├── snapshot.cpp       snapshot/restore of every setting the sweep changes
│   ├── sdk.*              connection, callback log, SDK_CALL tracking
│   ├── wireproxy.*        UDP recording proxy + ATEM field parser
│   ├── backup.*           backup, compare, restore
│   ├── transfer.h         macro / still transfer helpers
│   └── tests_*.cpp        the tests (tests_generated.cpp is generated)
└── gui/                   atem-sweep-gui: model, painted widgets, window
```

```powershell
cd sweep
cmake -B build -G "Visual Studio 17 2022" -A x64 `
    -DQt6_DIR="<Qt>/msvc2022_64/lib/cmake/Qt6" `
    -DATEM_SDK_DIR="<Blackmagic ATEM Switchers SDK 10.2.1>/Windows"
cmake --build build --config Release
```

Builds `atem-sweep.exe` and `atem-sweep-gui.exe` into `sweep\build\Release\`
(the GUI gets the Qt runtime next to it, via `windeployqt`). `ATEM_SDK_DIR` is
the SDK's `Windows` folder, with `BMDSwitcherAPI.h` in its `include` folder
(see [overview.md](overview.md#build)).
